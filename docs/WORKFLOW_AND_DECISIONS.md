# 工作流与关键决策

## 1. 从 demo 到批量处理

项目先选取一棵 root 树验证输入、输出、递归规则与验收结构。流程稳定后，以一部分树作为基线，其余范围按区间交给多个相互隔离的 AI 会话并行处理。

每个会话只允许写自己的树目录和 worker 报告，不得修改全局进度或其他会话的输出。总控阶段统一读取 worker 报告、抽样核对树与 JSON、检查 issue 是否闭环，再合并最终交付。

这种设计证明的是范围拆分、冲突预防和 AI 协作治理，不是运行时多智能体平台。

## 2. 三源证据优先级

1. PDF 或图像原文：判断引用是否真实出现的主要证据。
2. Excel 清单：确认 root、文件映射和指定提取章节。
3. 源 JSON：作为抽取线索，不直接视为正确答案。

当三者冲突时，不让 AI 自动猜测；保留 evidence，标记风险并交由人工决策。

## 3. 递归与终端叶子

- 从 root 的正式引用开始递归查找子文件。
- 有对应文件时继续展开；已展开节点不重复展开，避免循环。
- 上级文档明确出现、但本地缺少 PDF/JSON 或无法确认映射的引用，保留为 terminal leaf，不因“找不到文件”而删除。
- OCR 低置信、编号不清或文件内容错配进入人工复核队列。

## 4. 去重规则

- 原始文件字节 SHA-256 相同：归并，并通过 coverage 保留所有来源出现位置。
- 文件名相同但原始字节不同：不直接合并、不覆盖，全部保留并在交付文件名中增加来源与短 hash。
- 最终 manifest 记录交付文件、代表来源、hash、引用数和出现次数。

早期版本曾因按文件名归并而低估交付数量；为避免同名文件误删，最终口径改为保留所有原始字节不同的候选版本。源缓存、树内出现次数与交付文件不是同一总体。归档复审发现，解析并规范化 JSON 后仍有多组语义重复，因此更成熟的下一版应同时保留“原始证据 hash”和“规范化对象 hash”两层口径。

## 5. Human-in-the-loop

AI 适合承担：

- 批量读取与初步抽取；
- PDF/OCR/JSON 间的候选比对；
- 递归树与检查材料草拟；
- 解析、字段、hash、manifest 与 coverage 的批量检查。

人工承担：

- 低清内容与语义歧义判断；
- 缺失映射和信息性引用口径；
- 风险接受、返工决定与最终验收；
- 确认哪些材料允许进入最终交付或作品集。

## 6. 质量门禁

- 交付 JSON 全部可解析；
- 顶层与引用记录只出现允许字段；
- 最终文件名唯一；
- 最终原始字节 SHA-256 无重复组；
- manifest 覆盖所有交付文件；
- coverage 将每条树内记录映射到交付文件；
- 同名、字节不同候选清单中的变体全部保留；
- 争议项有 evidence、决策和变更记录。

## 7. 如果重做

- 为字段、类型、必填项和枚举建立正式 JSON Schema，而不仅是允许字段检查。
- 将解析、规范化、去重与 coverage 生成收敛为确定性流水线并加入单元测试。
- 为 reviewer 提供差异界面和低置信队列，而不是依赖散落的 Markdown。
- 建立抽样金标准与双人复核，才能估计语义准确率和召回率。
- 用可注入规则版本记录每次口径变化，避免不同会话漂移。
